## 요청 1 — 원본에 이미 있는 값 (복사만 하면 됩니다)

SC제일은행 `e-그린세이브예금` 원본 기준 실제 값입니다.

| 원본 칸 | 실제 값 | 우리가 담을 컬럼 | 없으면 |
| --- | --- | --- | --- |

## 요청 2 — 이미 추출해두신 값 (출력에 추가만 하면 됩니다)

### 2-1. 조건별 적용 기간 — 가장 급합니다

`min_term_months` / `max_term_months` / `applicable_term_months`.

부산은행 `LIVE정기예금` 이 대표적입니다. 원문이 이렇고,

```
가. 3~5개월  특판우대이율 : 0.60%
나. 6~11개월 특판우대이율 : 0.60%
다. 12개월   특판우대이율 : 0.55%
```

`ai_condition_cache.jsonl` 에는 정확히 파싱돼 있습니다
(`min=3,max=5` / `min=6,max=11` / `exact=12`).

그런데 최종 산출물에서는 **6개 만기 행 전부에 3개 조건이 똑같이 붙습니다.**
1개월 행에도 "3~5개월", "6~11개월", "12개월" 조건이 다 붙어 있습니다.
이렇게 적용 범위 밖에 붙은 경우가 확인된 것만 172건입니다.

만기별로 상품 행을 나누셨으니 조건도 해당 만기에만 붙이려던 설계로 이해했는데,
`_period_bounds()` 가 없어진 걸 보면 거르는 부분이 아직 안 들어간 것 같습니다.
**거르는 건 BE 가 해도 됩니다 — 대신 이 세 값을 산출물에 실어주세요.**
받으면 `product_condition.applies_period_min` / `applies_period_max` 에 넣고
만기와 비교해서 저희가 거르겠습니다.

### 2-2. 상품별 우대 상한

`overall_max_bonus_rate`. 원문에 "최고 우대금리 X%p" 처럼 개별 조건을 다 더해도 넘을 수
없는 상한이 적힌 경우의 값으로 이해했습니다. 캐시 868건 중 **645건(74%)** 에 채워져 있는데
최종 산출물에는 없습니다. 상품 단위 값이라 `product.jsonl` 쪽에 컬럼 하나로 주시면 됩니다.

### 2-3. 조건 기준값·단위

`threshold_value` / `threshold_unit`. develop 에는 있는데(PR #5)
`feature/extraction-pipeline` 산출물에는 없습니다. 아래 "브랜치" 항목과 같은 원인으로 보입니다.

## 요청 3 — 새로 뽑아야 하는 값

이건 실제 작업이 필요한 것들이라 부담이 있을 것 같습니다. 우선순위를 붙였습니다.

| 우선 | 필요한 값 | 상황 |
| --- | --- | --- |
| 높음 | **적금 월 납입 한도** (`monthly_min` / `monthly_cap`) | 금감원에 별도 칸이 없고 약관 줄글에만 있습니다. 저희가 사용자에게 **월 저축액**을 받아 추천하는데, 이 값이 없으면 월 한도를 넘는 상품을 추천하게 됩니다. 지금 오는 `amount_cap` 은 총 한도라 다릅니다 |
| 낮음 | 가입 연령 제한 | 청년 전용 상품 등 |
| 낮음 | 신규고객 전용 여부 | `spcl_cnd` 줄글 안에 있습니다 |

## 검산(`verification_status`)은 BE 가 맡겠습니다

산출물의 `verification_status` / `confidence_badge` 가 전부 비어 있던데, **저희가 임포트
시점에 계산해서 채우겠습니다.** 어차피 사용자별 금리 계산 로직을 BE 가 짜야 하고, 검산은
거기에 "모든 조건을 충족한다고 가정"만 넣으면 나오는 값이라 로직이 같습니다.

다만 **요청 2-1(기간)과 2-2(상한) 없이는 계산이 맞지 않습니다.** 저희가 직접 돌려본 결과입니다.
조건 합계(택1 그룹은 최댓값)와 공시 우대폭(`max_rate - base_rate`)을 비교한 것입니다.

```
은행·저축은행 474개 상품행 기준, "조건 합계 > 공시 우대폭" 인 건수

  지금 산출물 그대로            211건 (44%)
  + 우대 상한(2-2) 반영         174건 (36%)
  + 우대 상한 + 기간(2-1) 반영  127건 (26%)
```

두 값만 받아도 오차가 40% 줄어듭니다. 남는 26% 가 실제로 추출이 어긋난 건들이고,
그건 저희가 `MISMATCH` 로 찍어서 `confidence_badge = '검수대기'` 로 내리겠습니다.

## 산출물을 어떻게 주고받을까요

`.gitignore` 처리(멘토님 지적 반영)로 산출물이 레포에 안 올라오는데, 그러다 보니 BE 가 받을
경로가 없습니다. 지금은 삭제 전 커밋에 남아 있는 파일을 꺼내 쓰고 있습니다.

`ai/docs/architecture-decisions.md` §5 에 *"AI 코드는 BE 의 FastAPI 앱 안에 모듈로 들어가고
DB 도 공유"* 라고 적어두신 걸 봤는데, 그 방향이면 파일 전달이 아니라 모듈 연동이 맞을까요?
방식이 정해지기 전이라도 **임포터 개발용으로 현재 산출물 2개를 한 번 공유**해주시면
바로 검증해볼 수 있습니다.

## 요청하지 않는 것 (BE 가 처리합니다)

혹시 중복 작업이 될까 봐 적어둡니다.

| 항목 | BE 처리 방법 |
| --- | --- |
| 기관 코드 | `product_id` 앞부분에서 잘라냅니다 (`CU-01235-…` → `CU-01235`) |
| 적립방식 (정액/자유) | `product_type` 문자열에서 뽑습니다 (`"적금(자유적립식)"`) |
| 만기별로 복사된 우대조건 | 상품 단위로 중복 제거합니다 (7,068 → 2,426) |
| 기관명 중복 | `'국민은행'`(은행)과 `'국민은행'`(직장 신협)처럼 이름이 같은 기관 5곳은 종류를 붙여 구분합니다 |
| `batch_run` / `run_id` | 임포트 시 BE 가 생성합니다 |

**파일 모양은 편하신 대로 주셔도 됩니다.** BE 테이블 모양에 맞추실 필요 없습니다 —
그 변환은 임포터가 흡수합니다. 위 목록은 "모양"이 아니라 "값이 없어서 못 채우는 것"입니다.
